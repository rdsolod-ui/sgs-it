# Источник заявки и Telegram outbox

Инкремент P5–P6 подготовлен 2026-09-22. Реальные уведомления и фиксация источника по умолчанию выключены. 2026-09-24 код `1b245d7` опубликован на VPS вместе со сценарным диалогом. Служба уведомлений не включена: установка кода не активирует Telegram.

## Источник

`ATTRIBUTION_ENABLED=true` действует только с готовыми реквизитами/контактом оператора и `LEGAL_READY=true`. Браузер передаёт на `/api/session` очищенные метки; сервер очищает их повторно. Сохраняются только разрешённая категория страницы (`/` или `/sgs-it/`), hostname перехода и короткие UTM-метки. Произвольные пути, query/hash, userinfo, email, телефоны, длинные последовательности и похожие на секреты значения не принимаются. Это минимизация, не гарантия обезличивания любых возможных меток.

Первое и последнее посещение имеют серверное время. Нет дополнительных analytics cookies или localStorage: записи связаны с уже существующей сессией. Preview не отправляет метки и не сохраняет их. Метка Telegram появляется только после проверки подписанного initData; новый вход со страницы сбрасывает прежнюю отметку до новой проверки. Метки посетителя не доказывают рекламную причинность.

В заявку транзакционно записывается снимок источника. Он доступен в карточке и CSV/XLSX вместе с профилем; экспорт сохраняет защиту от формул. Неизвестный источник явно обозначен. Session-источник удаляется по сроку чата, снимок — вместе с заявкой.

## Доставка

Миграция `004_attribution_outbox` добавляет источники, outbox, историю попыток и heartbeat обработчика. Задание создаётся в той же транзакции, что заявка и согласия. Уникальность `lead_id + event` подавляет дубли; повтор формы возвращает прежнюю заявку. При выключенном флаге задания не создаются, поэтому включение не запускает рассылку по всем старым лидам.

В очереди нет копий контактов, брифа и переписки. Перед отправкой обработчик читает существующую заявку и последние отдельные согласия на данные/обратную связь; отзыв останавливает задание. Шаблон содержит ограниченные поля, подтверждённость резюме, источник, версию согласий и ссылку `/admin?lead=<uuid>`. Пользовательский HTML экранируется, ссылка требует обычной авторизации.

Состояния: `pending → leased → sending → sent`; подтверждённая временная ошибка → `retry`, постоянная/исчерпанные попытки → `failed`. Claim использует `FOR UPDATE SKIP LOCKED`, lease и отдельную историю попыток. Процесс не держит SQL-транзакцию во время HTTP-запроса.

- 429 учитывает `retry_after`; подтверждённые 5xx с `ok=false` имеют ограниченные повторы. Не более пяти автоматических попыток; оператор может назначить ещё одну после устранения причины.
- Таймаут, сетевой сбой, невалидный ответ или истёкший lease после начала отправки дают `uncertain`. Автоповтора и кнопки слепой повторной отправки нет. Нужно сверить канал; автоматическое разрешение неоднозначности в этот инкремент не входит.
- Истёкший lease до начала отправки можно забрать повторно. Изменение целевого канала/бота не перенаправляет старые задания автоматически.
- Если заявку удалили до отправки, задание отменяется. Если сообщение уже отправлено, сохраняются только необходимые routing/message identifiers и запрашивается удаление. При удалении заявки во время HTTP-запроса сообщение может кратко появиться; успешный ответ сохраняет ID для следующего удаления. При неизвестном исходе ID может отсутствовать — автоматическое удаление тогда невозможно.
- Удаление ограничено Telegram API (в частности, временем и правами); неудача остаётся видимой в CRM. Удаление чужих копий и пересылок не обещается. Завершённые обезличенные записи отмены/удаления очищаются через 30 дней; неразрешённые ошибки сохраняются для оператора.

## Настройки перед реальным запуском

В защищённом `/etc/sgsit/app.env`, не в Git:

- `TELEGRAM_NOTIFICATIONS_ENABLED=true`, `TELEGRAM_NOTIFICATIONS_APPROVED=true`.
- `LEGAL_READY=true`, готовые `OPERATOR_REQUISITES` и `PRIVACY_EMAIL`.
- Проверенная `LEGAL_POLICY_VERSION` и точный согласованный текст `TELEGRAM_NOTIFICATION_NOTICE`: он добавляется к политике и отдельному согласию. Шаблон документов сам по себе не считается готовым юридическим основанием.
- Отдельные `TELEGRAM_NOTIFICATION_BOT_TOKEN`, `TELEGRAM_NOTIFICATION_BOT_ID`, `TELEGRAM_NOTIFICATION_CHAT_ID`. Mini App token автоматически не используется.
- `APP_ORIGIN` — HTTPS origin сайта. Исключение loopback HTTP существует только для `NODE_ENV=test`.

Получатель задаётся сервером. Обработчик при старте проверяет getMe, getChat и getChatMember: совпадение бота, канал без публичного username и право публикации. Доступ сотрудников и допустимость передачи проверяет оператор. URL Telegram фиксирован в коде, пользователь и очередь не могут назначить произвольный HTTP endpoint.

После проверенного выпуска и синтетической приёмки можно установить `deploy/sgsit-notifications.service` и запустить службу. Обычный bootstrap её не устанавливает и не включает. CLI: `npm run notifications:worker -- --once` для одного цикла либо без `--once` для процесса. При выключенной конфигурации CLI завершается без сетевого вызова.

Перед заменой release/откатом остановить notification worker; затем проверить совместимость миграции и запустить его из нового release только при готовых настройках. Настройки читаются при старте: при отключении необходимо остановить worker и перезапустить API с выключенным флагом. Не удалять outbox при откате. Совместимые добавленные таблицы/колонки можно оставить для прежнего API.

CRM показывает очередь, возраст ожидания, ошибки, неизвестный исход и наличие свежего heartbeat. Ручной повтор доступен авторизованному оператору только для `failed`, записывается в admin audit и не выполняет сетевой вызов из HTTP-транзакции.

## Проверки и границы

`npm run test:outbox` использует отдельную loopback PostgreSQL с именем `_test`/`_ci` и внедрённый mock transport. Проверяются транзакция, дедупликация, два обработчика, 429/403, неизвестный исход, перезапуск, удаление до/во время отправки, смена адресата, согласия/отзыв, серверный источник и доступ. Реальный Telegram API не вызывается.

`npm run test:notifications-browser` проверяет CRM, авторизацию ссылки, повтор после ошибки, запрет повтора uncertain и доступность. Синтетическая конфигурация включается только в отдельном шаге CI; worker CLI с настоящим transport там не запускается.

Остаток P5–P6: проверка реального бота/канала и согласованных условий, синтетическая доставка в выбранный канал перед приёмом реальных лидов, процедура ручного разрешения `uncertain`; дополнительные добровольные поля профиля и назначения сотрудников. AI, обучение и платежи не включены этим инкрементом.

Официальные контракты проверены 2026-09-22: [sendMessage](https://core.telegram.org/bots/api#sendmessage), [ResponseParameters](https://core.telegram.org/bots/api#responseparameters), [deleteMessage](https://core.telegram.org/bots/api#deletemessage).
