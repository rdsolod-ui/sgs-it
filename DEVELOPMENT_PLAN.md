- Сохраняем текущий стек и PostgreSQL; для первой очереди доставки не добавляем отдельный брокер.

## Architecture Overview — архитектура продолжения

```text
Посетитель → UI / маскот → серверный менеджер диалога
                              ├─ этап воронки и профиль
                              ├─ проверенная база знаний и офферы
                              ├─ AI-адаптер, лимиты и разрешённые действия
                              └─ форма контактов и согласий
                                         ↓
                         PostgreSQL: лид + согласия + outbox
                                         ↓
                    CRM ← очередь доставки → приватный Telegram-канал
                     ↓
            квалификация → пресейл/заказ → аудит → основное предложение
                     ↓
      разрешённые обезличенные примеры → разметка → eval → новая версия
```

Предлагаемое разделение кода: оркестрация диалога, знания, реестр офферов, уведомления, атрибуция и оценка качества — самостоятельные модули с контрактами. Извлекать их из существующего сервера постепенно, сохраняя текущие тесты.

Публичный preview продолжает работать на синтетических данных. Контакты и серверные результаты остаются в закрытом рабочем контуре; клиент не выбирает SQL, адрес доставки, произвольный URL или инструмент модели.

### P2. Маскот как SaaS sales manager

Реализовать серверную машину состояний — явные этапы и правила перехода. Посетитель может перескочить к цене, контакту или демо, вернуться к вопросу, отказаться и завершить разговор. Не заставлять проходить весь опрос перед контактом.

| Этап | Поведение | Какие данные уточняем | Условие перехода |
|---|---|---|---|
| Приветствие | Представиться AI-консультантом SGS IT, предложить помощь | Язык, намерение | Пользователь выбирает направление или задаёт вопрос |
| Краткая презентация | 1–2 предложения о пользе parkops без перечня всех функций | Первичный интерес | Предложен один релевантный вопрос |
| Профилирование | По одному вопросу, учитывать уже сказанное | Роль, отрасль, масштаб, текущие системы | Минимальный профиль либо явный пропуск |
| Потребности | Уточнить проблему, последствия, желаемый результат | Процессы, показатели, сроки, доступность данных | Пользователь подтверждает резюме потребности |
| Решение и демонстрация | Связать потребность с подтверждённой функцией | Подходящий модуль, ограничения | Понятна предлагаемая ценность |
| Возражения | Признать вопрос, уточнить причину, дать проверяемый ответ | Бюджет, доверие, внедрение, полномочия | Возражение прояснено либо нужна помощь человека |
| CTA первого контакта | Предложить аудит/демо/встречу и отдельную форму | Выбранная услуга и канал | Сервер подтвердил создание заявки |
| CTA платного пресейла | Показать состав, условия и цену опубликованного оффера | Выбор предложения | Заказ/счёт создан; оплата подтверждается отдельно |
| Завершение/передача | Подтвердить фактический результат и следующий шаг | Ответственный/срок, если назначены | Лид в CRM либо добровольное завершение |

- [ ] Структурированный ответ AI: текст, предлагаемый переход, разрешённое действие, ссылки на источники знаний, обновление профиля. Сервер проверяет схему и допустимость действия.

| РОП | Квалификация, этапы сделок, причины потерь, качество лида, SLA, следующий шаг | Оценка потребности и сделки, а не личной ценности человека |
| SaaS-инженер | Интеграции, API, источники данных, роли, миграция, доступность, ограничения | Не обещает совместимость без технической проверки |
| Аналитик данных | Качество данных, источники, определения метрик, воронки, атрибуция, проверка гипотез | Различает корреляцию/причину, факт/оценку |
| Финансист | P&L, ДДС, баланс, маржа, unit economics, сценарии окупаемости | Формулы и единицы проверяемы; прогноз помечен и зависит от допущений |
| Финансовый учёт | Связь продаж, платежей, затрат, начисления и движения денег | Юрисдикция/период указаны; вопросы конкретного учёта передаются специалисту |
| Методики продаж | Рабочие сценарии discovery, SPIN; элементы BANT/MEDDICC для подходящих B2B-сделок | Методики изучить по первоисточникам; применять адаптивно, не как обязательный допрос |
| Product/Customer Success | Внедрение, первый полезный результат, обучение команды, сопровождение | Условия берутся из актуального оффера |

- [ ] Создать реестр источников: URL/автор, дата получения, область, лицензия/допустимое использование, версия, срок проверки, ответственный за проверку.
- [ ] Использовать официальную документацию, разрешённые материалы компании и первичные профессиональные источники. Публичная доступность не означает право копировать материал целиком или обучать на нём модель.
- [ ] Разделить продуктовые факты, профессиональные методики, нормативные материалы и гипотезы. Конфликт фиксировать, не объединять незаметно.
- [ ] Организовать поиск по утверждённым материалам (RAG): сначала компактный корпус и поиск PostgreSQL; векторный индекс добавлять после измерения необходимости.
- [ ] Возвращать в генерацию только релевантные фрагменты в лимите контекста. Документы/сайты — данные, не инструкции для доступа к инструментам.
- [ ] Проверять свежесть, противоречия и заражённые инструкции; устаревшие/непроверенные материалы не выпускать автоматически.
- [ ] Финансовые вычисления выполнять проверяемыми функциями; язык модели используется для объяснения результата.

**Готово, когда:** можно восстановить источник утверждения, откатить версию знаний и безопасно ответить «недостаточно данных».

### P4. Подключение и контроль AI

- [ ] До вызовов проверить доступность конкретной API-модели в аккаунте, её актуальные параметры, цены и допустимость фактической схемы использования. Названия Luna/Astra в прежнем коде отражают пожелание и конфигурацию, не подтверждённую доступность API.
- [ ] Проверить путь данных и раскрытия пользователю. Контакты формы не передавать модели; текущего regex-маскирования недостаточно для гарантированного обезличивания свободного текста.
- [ ] Сохранить лимиты на каждый запрос, контекст, вывод, сессию и общий расход. Профиль/знания/системные инструкции учитывать в общем бюджете.
- [ ] Текущие значения кода: ввод 700 токенов локального счётчика, output 1200, видимый ответ 450; контекст ограничивается 6000 UTF-8 байт, хотя переменная названа AI_CONTEXT_TOKENS. Устранить двусмысленность без бесконтрольного увеличения затрат.
- [ ] Проверить текущую частоту и дневные лимиты; стоимость резервировать до вызова. Не копировать старые ценовые коэффициенты без проверки.
- [ ] Общая квота должна включать ответы, резюме, классификацию, поиск/эмбеддинги и eval. Fine-tuning не расходует исходный бюджет без отдельной оценки.
- [ ] Обработать timeout, 429, невалидную структуру, недоступную модель и недостаток бюджета: честный резервный сценарий, без скрытого переключения на дорогую модель.
- [ ] Провести небольшую платную проверку только после готовности конфигурации; измерить качество, стоимость и задержку.

**Готово, когда:** проверены реальная модель и счётчик затрат; ограничения невозможно обойти через параллельные запросы; отказ провайдера не блокирует контакт с менеджером.

### P5. Лид, источник и мини-CRM

- [ ] Согласовать профиль: роль, отрасль, масштаб, системы, проблема, желаемый результат, сроки, бюджет при добровольном сообщении, полномочия, возражения, выбранный оффер.
- [ ] Каждое поле имеет происхождение: слова пользователя, результат правила или предположение AI. Неизвестные сведения оставлять неизвестными.
- [ ] Добавить краткое резюме, подтверждённое пользователем, и отдельную служебную рекомендацию менеджеру.
- [x] Добавить источник: очищенные landing/referrer, разрешённые UTM, first/last touch при допустимом хранении, сайт/Mini App, время, версия сценария, выбранный CTA. Не сохранять произвольные URL-параметры и секреты.
- [ ] Показывать «источник не определён», когда данных нет; referrer/UTM являются наблюдаемыми метками и не доказывают рекламную причинность.
- [ ] Завершить документы/реквизиты/условия обработки и сценарии согласий до открытия реальных форм. Отдельно решить использование диалогов для улучшения и передачу в Telegram.
- [ ] Расширить карточку CRM: резюме, источник, оффер, качество заполнения, следующий шаг, ответственный, срок, доставка уведомления, результат контакта.
- [ ] Этапы разговора и сделки хранить отдельно: например, new → contacted → qualified → presale_offered → awaiting_payment → paid → delivery → completed/lost. Финальный перечень утвердить.
- [ ] Защитить от дублей и чужих id; проверить выгрузки, формульные инъекции CSV/XLSX, историю изменений и удаление.

**Готово, когда:** менеджер понимает запрос без перечитывания всей переписки; профиль и контакты сохраняются транзакционно и доступны только авторизованным сотрудникам.

### P6. Telegram-бот уведомлений в приватный канал

**Цель:** после успешного сохранения заявки отправить команде полезное уведомление. Получатель — заранее настроенный приватный канал, а не адрес из пользовательского ввода.

- [ ] Получить идентификатор нужного канала и защищённо настроить бота. Проверить тип/название канала, состав доступа и право бота публиковать; начать с синтетической заявки.
- [ ] Согласовать обработку контактов в Telegram как отдельную передачу данных. Приватность канала сама по себе не решает вопросы хранения/получателей.
- [x] Добавить notification_outbox в той же транзакции, что лид и согласия. Не вызывать Telegram из незавершённой транзакции и не откатывать заявку при сбое Telegram.
- [x] Отдельный worker забирает задания с блокировкой/lease, фиксирует попытку, доставку, message_id, ошибку и следующую попытку.
- [x] Уникальный ключ lead + event + version подавляет повторное создание задания. При неоднозначном сетевом timeout помечать uncertain: Telegram не даёт здесь гарантии exactly-once, слепой повтор может дать дубль.
- [x] Обработать rate limit/retry_after, временные ошибки, отсутствие прав, удалённый канал и перезапуск worker; конечные ошибки показывать в CRM с возможностью безопасного повтора.
- [x] Формировать сообщение из структурированных данных; контакты подставлять на сервере, резюме — из разрешённых полей. При недоступности AI отправлять проверяемое шаблонное резюме.
- [x] Экранировать разметку, ограничивать размер, не публиковать всю переписку, секреты, IP и ненужные данные. При переполнении — короткое резюме и защищённая ссылка в CRM.
- [x] Кнопка «Открыть лид» ведёт в CRM с обычной авторизацией; URL не содержит контакт или токен входа. Маршрут карточки с id нужно реализовать и проверить.
- [ ] Сохранить связь заявки с сообщением для обновлений и удаления. Разработать процедуру удаления в доступных API пределах; не обещать удаление чужих копий/пересылок.
- [x] Контроль доставки: возраст очереди, число ошибок, повторов, uncertain. Сбой самого Telegram должен быть виден в админке/мониторинге независимо от канала.
- [ ] Кнопки «Взять в работу»/«Назначить» — следующий инкремент с проверкой сотрудника и подписи callback; в MVP достаточно ссылки в CRM.

Предлагаемый шаблон, все значения заполняются только известными сведениями:

```text
Новая заявка SGS IT · № {lead_id} · {дата и время}
Имя / компания / роль: {подтверждённые поля}
Контакт: {выбранный канал и контакт}
Запрос: {1–3 предложения о задаче и желаемом результате}
Контекст: {системы, масштаб, сроки — если сообщены}
Интерес: {аудит / демо / встреча / платный пресейл}
Возражения: {подтверждённые либо «не зафиксированы»}
Источник: {сайт или Mini App; очищенные UTM/referrer}
Следующий шаг: {рекомендация; ответственный, если назначен}
Согласия: {статус и версия; без полного текста}
Открыть лид: {защищённая ссылка CRM}
```

Основные API-параметры и ограничения сверять с [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage); обработку задержки повторов — с [ResponseParameters](https://core.telegram.org/bots/api#responseparameters). Это проектная очередь доставки, не обещание гарантированной доставки со стороны Telegram.

**Готово, когда:** сохранённый лид не теряется при недоступности Telegram; штатная повторная отправка формы не создаёт второе уведомление; канал получает корректное сообщение, а CRM показывает результат доставки.

### P7. Покупка пресейл-продукта и выполнение

- [ ] Определить состав платного результата и связь с уже реализованным документом аудита.
- [ ] Выбрать первый вариант: заявка + счёт от менеджера либо онлайн-платёж. Условия договора/оплаты/возврата и применимые требования проверить до запуска.
- [ ] Хранить снимок оффера, цену, валюту, состав, заказ и историю статусов независимо от последующих изменений каталога.
- [ ] Для онлайн-оплаты: серверное создание платежа, идемпотентность, проверка подписи webhook, сверка суммы/валюты/order_id, повторы и возвраты. Возврат браузера с платёжной страницы не считается доказательством оплаты.
- [ ] Для счёта: подтверждение оплаты уполномоченным сотрудником с журналом и основанием, не словами пользователя в чате.
- [ ] После оплаты назначать следующий шаг, собирать входные материалы и готовить аудит; выдача документа не означает автоматическую отправку клиенту.
- [ ] Связать результат пресейла с обоснованным предложением подписки/внедрения/сопровождения.

**Готово, когда:** оплаченный заказ однозначно связан с лидом и оффером, повтор webhook не создаёт повторных операций, клиенту понятны результат и следующий шаг.

### P8. Улучшение на диалогах и результатах продаж

Три независимых механизма:

1. Контекст текущего диалога — для ответа этому посетителю.
2. Курируемое улучшение базы знаний, сценариев и инструкций — по разрешённым примерам и обратной связи.
3. Возможное дообучение весов модели — отдельный проект после проверки качества датасета, прав, модели и бюджета. Разговор с пользователем сам по себе веса не меняет.

- [ ] Определить основание и уведомление об использовании диалогов для улучшения; где требуется — отдельный добровольный выбор, не связанный с доступом к услуге. До этого использовать синтетические примеры.
- [ ] Разделить рабочие диалоги, идентификационные данные, разрешённый учебный корпус и неизменяемый тестовый набор.
- [ ] Обезличивать контакты, имена, названия компаний, редкие идентифицирующие сочетания и коммерческие сведения; проверять риск повторной идентификации. Regex по телефону/email недостаточен.
- [ ] Добавить разметку: этап, намерение, потребность, возражение, корректность ответа, полезность, потеря/продвижение, оценка менеджера, последующий результат сделки.
- [ ] Не считать любой исход доказательством качества: покупка не оправдывает ложное обещание, отказ не всегда ошибка продавца.
- [ ] Превращать повторяющиеся вопросы в кандидаты FAQ; новые факты о продукте подтверждать у владельца/по документации.
- [ ] Единичный диалог и внешний сайт не меняют общие инструкции автоматически. Кандидат → проверка → версия → eval → ограниченный выпуск → наблюдение → откат при регрессии.
- [ ] Разделять train/dev/test по диалогу и компании, удалять дубликаты, использовать временной holdout; исключить утечку проверочных ответов в обучение.
- [ ] Версионировать источник/датасет/сценарий/модель/цены/результат eval и связывать их с выпущенной версией.
- [ ] Распространять удаление/отзыв на учебные копии и индексы, вести минимальный журнал. Для обученных весов заранее определить ограничения удаления и порядок замены модели.
- [ ] В админке создать раздел «Качество и знания»: очередь примеров, редактирование, допуск, источники, версии, сравнение результатов, откат.
- [ ] Запускать цикл улучшения сначала вручную по накоплению материала; расписание и автономное обучение не включать этой задачей.

В основе — измерение качества, улучшение инструкций/контекста и лишь затем оценка целесообразности fine-tuning; актуальные варианты сверять с [OpenAI Model optimization](https://developers.openai.com/api/docs/guides/model-optimization). Конкретная схема хранения и допуска в этом плане — проектное предложение.

**Готово, когда:** новая версия улучшает проверяемые сценарии без критических регрессий, её происхождение объяснимо и доступен откат.

### P9. Mini App, PWA, эксплуатация и пилот

- [ ] Подключить клиентский Telegram Mini App; проверить initData, срок/подпись, настройки домена и возврат в чат. Не путать с ботом внутренних уведомлений.
- [ ] Проверить физические iPhone/Android: клавиатура, safe areas, ориентация, светлая/тёмная тема, фон, обновление PWA, офлайн.
- [ ] Перепроверить зависимости, нагрузку, screen reader, лимиты, мониторинг расходов и доступность восстановления БД из внешней резервной копии.
- [ ] Собирать воронку событий без сырого текста и контактов в аналитических метках; определить допустимое хранение и согласия.
- [ ] Провести ограниченный пилот, получить обратную связь сотрудников, разобрать потери и утвердить следующий релиз.

**Готово, когда:** сквозной путь проверен в целевых клиентах, уведомления и восстановление работают, коммерческие метрики имеют исходную базу.

## Данные и миграции — предлагаемые сущности

Существующие leads/messages/consent_events/activities/ai_usage/lead_audits переиспользуются. Новые имена и состав проверить перед миграцией:

| Сущность | Минимальное назначение |
|---|---|
| conversation_state | Этап, версия сценария, профиль, ссылка на visitor, версия для конкурентного обновления |
| lead_profile / lead_attribution | Подтверждённые сведения, происхождение полей, очищенный источник, версия резюме |
| offers / orders / payment_events | Версия коммерческого предложения, заказ, подтверждённые события оплаты |
| notification_outbox | Событие, lead_id, состояние, попытки, lease, срок повтора, message_id; без лишней копии контактов |
| knowledge_sources / knowledge_versions | Источники, права использования, проверка, актуальность и версии |
| learning_candidates / eval_runs | Разрешённые примеры, разметка, происхождение, разделение наборов, отчёты качества |

Миграции — версионированные и совместимые с предыдущим runtime; финансовая история требует отдельной политики хранения. Перед внедрением проверить каскады удаления, бэкапы, права и индексы. Отдельный векторный сервис и мультимодельная система пока не нужны без измеренного основания.

## Тесты и критерии приёмки

Числа ниже — предложенные инженерные критерии для согласования, не результаты уже выполненных тестов и не прогноз конверсии.

| Область | Проверки | Критерий |
|---|---|---|
| Воронка | Все этапы, возврат, пропуск, сразу цена/контакт, отказ, повторный посетитель | Нет тупиков/навязчивых повторов; один понятный следующий шаг |
| Профиль | Противоречия, неизвестные поля, исправление пользователем, конкурентные сообщения | Нет выдуманных данных и перезаписи нового профиля старым ответом |
| Знания | Подтверждение функции, устаревший/конфликтующий источник, вредоносные инструкции | Непроверенное утверждение не становится обещанием или командой |
| Продажи | Возражения, бесплатный/платный оффер, неподходящий клиент | Нет выдуманных цен/гарантий; корректная передача человеку |
| Финансы | Формулы, периоды, валюты, НДС-параметры, нули и пропуски | Эталонные расчёты совпадают; допущения показаны |
| Приватность | Чужая сессия, контакт в чате/UTM, отказ от обучения, удаление | Ноль утечек в обязательном наборе; контакт не попадает в AI/логи/аналитику |
| AI и затраты | Параллельные вызовы, лимит, timeout, 429, ошибка структуры | Расход учитывается; резервирование атомарно; нет обхода квоты |
| CRM | Повтор формы, сохранение согласий, права, CSV/XLSX, профиль/источник | Одна заявка на requestKey; сведения и доступ корректны |
| Telegram | 429, timeout после отправки, 403, перезапуск, удаление лида, HTML-инъекция | Лид не потерян; штатные дубли подавлены; uncertain виден оператору |
| Пресейл | Подмена цены, чужой order_id, поддельный/повторный webhook, возврат | Только подтверждённая оплата меняет финансовый статус |
| Обучение | Дубли train/test, загрязнение, отозванный пример, откат версии | Проверочный набор независим; версия воспроизводима |
| UI и маскот | Mobile, WebKit/Chromium/Firefox, reduced motion, keyboard/screen reader | CTA доступен, нет перекрытий и ложного статуса успеха |
| Выпуск | Migration, manifest, health, backup restore, rollback | Проверен именно установленный commit и рабочие данные сохранены |

### Оценка качества AI и эффективности продаж

- Начать с не менее 60 синтетических сценариев: роли/отрасли, потребности, возражения, готовность купить, отказ, недостаток знаний, атаки и сбои. Это предлагаемый стартовый объём.
- Критические сценарии приватности, авторизации, платежей и недостоверных обещаний должны пройти полностью; одной средней оценки недостаточно.
- Экспертная оценка: точность, релевантность, краткость, правильность этапа, качество вопроса, обоснованность CTA, полезность передачи менеджеру. Предлагаемый проходной уровень 4/5 без ухудшения критических групп.
- Замерять задержку p50/p95, стоимость диалога и квалифицированного лида; пороги установить после измерения на выбранной модели.
- Воронка: начало диалога → подтверждённая потребность → CTA → валидная заявка → первый контакт → предложение пресейла → оплаченный заказ → выполненный аудит → основная продажа.
- Для каждой конверсии определить знаменатель, окно атрибуции и дедупликацию. Исключать тесты/ботов; не объединять оплату и заявление о намерении купить.
- До достаточной выборки показывать наблюдения без заявлений о статистически доказанном росте. Контрольные метрики: жалобы, отказы, ошибочные обещания, отписки, возвраты и качество лидов.

## Potential Gotchas — известные ограничения

- Текущий AI-промпт в server/index.ts короткий, live-ответ заменяет текст сценарного ответа; это ещё не полноценная оркестрация продажи и действий. Нужен явный контракт, а не только более длинный prompt.
- В коде смешано имя лимита «токены» и фактический контроль UTF-8 байт. При RAG и профиле легко случайно превысить контекст или обрезать смысл.
- Текущее маскирование телефона/email не делает произвольный диалог обезличенным. Пользовательские слова не должны автоматически становиться общим знанием.
- Наличие подписи Telegram Mini App не означает готовность уведомлений, доступа к каналу или его privacy-процессов.
- Серверное сохранение заявки, доставка уведомления, первый контакт и оплата — четыре разных события.
- Для документации не нужен повторный deploy приложения. Для кода использовать точные CI-артефакты.
- Маркетинговый каталог редактируют другие сотрудники: точечный diff, свежий SHA guard и сохранение ACL. Локальная копия общего каталога может отставать от live.
- При копировании прав изменённого HTML обновлять mtime, иначе одинаковый размер/старый mtime могут сохранить ETag и устаревший кеш.
- Browser QA с синтетическими insets не доказывает качество на физическом iPhone.
